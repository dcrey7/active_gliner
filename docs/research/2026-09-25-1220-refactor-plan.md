Rule: use `gliner2` for everything it does well. Build only the gaps. Keep the thesis observability (curves, logs, confidence bins, error lists, LLM cost stats) and make it task-agnostic.

## 1. What gliner2 2.0.0 gives us (we do not rebuild it)

| Need | gliner2 piece |
|---|---|
| Load student | `AutoExtractor.from_pretrained(<snapshot folder>, map_location="cuda")` |
| Batch inference with confidence and offsets | `batch_extract(..., include_confidence=True, include_spans=True)` |
| All 10 classification probabilities, empty label set allowed | `Classifier(m).batch_score(...)` |
| Relation pair score | one `confidence` per (type, head, tail) |
| Below-threshold candidates | `JointIEEngine(m).score(...)` (public), or abstention off |
| LoRA training, fixed steps, dev eval, best checkpoint, early stopping, seed, bf16, grad accumulation | `ExtractorTrainer` + `TrainingConfig` + `compute_metrics` hook |
| Training data format and checks | `InputExample`, `TrainingDataset.validate()` |
| Adapters | PEFT folders `best` and `final`; `PeftModel.from_pretrained`; `merge_and_unload` |
| Curves data | `train_metrics_history` (loss, learning rate, throughput per logging step) and `eval_metrics_history` in the `train()` result |

## 2. Gaps we build (from the package study, section 6.2)

1. **Pinning** - `AutoExtractor(revision=)` pins only `config.json`. Load from `snapshot_download(repo, revision=sha)`. Pin `gliner2==2.0.0`. Add `protobuf`.
2. **Fresh model per run** - LoRA changes the model object in place. Every run and seed loads a new base model.
3. **Below-threshold candidates (slots only)** - only the slot empty-output rule needs them. They come from the **same schema** used for prediction: the structure schema (`mode=None`) called again with `threshold=0.0` (structure fields have no abstention gate); with the entity-schema fallback, abstention off (`abstention_threshold=1.0`) and `threshold=0.0`. `JointIEEngine.score` is not used: it compiles a different schema and skips non-entity queries. Both the candidate call and normal prediction use `overlap_policy="allow"`, so the package's own flat decoder (which maximises total score and can swap one 0.6 span for two 0.4 spans) never runs; our greedy decoder (item 4) is the only overlap rule. A test checks that the 0.5-threshold output is a subset of the 0.0 output with equal scores. Candidate caps (pool 192, top-k 24) limit coverage; stated.
   Relations keep the signed-off rule: no predicted pair gives c = 0. Relation confidence is the pair score (no "proxy" wording). The paper states that pairs need both arguments at 0.2 or more.
4. **Flat decoding across labels** - the package lets one span carry two labels. Our decoder sorts all predicted spans by descending score and accepts a span only if it overlaps no accepted span (greedy). Ties break by (start, end, label name). Frozen before runs. We report the overlap rate before decoding.
5. **Word splitter** - the default keeps `Lithium-induced` as one token, so `Lithium` cannot be predicted. O2 measures, on the frozen **dev** labels only, the share of gold spans not aligned to word tokens per dataset. If above 0.5% (a declared heuristic), a splitter that also splits on hyphens is used for that dataset at training and inference. Residual alignment failures on every split are reported.
6. **Hallmarks** - decisions and scores from `Classifier` (empty set allowed), never from `classify_text` (forces one label).
7. **Slot JSON** - never `extract_json` (record mode returns `{}` when the first field is absent). Primary: `Schema.structure("slots", mode=None)` with one list field per slot type, trained with `Structure(..., mode=None)`, so the task is real JSON extraction. In the paper this is "aggregate slot extraction" (it does not use the record decoder). Fallback, chosen once on en-US dev zero-shot before any run, both at threshold 0.5 with the canonical (slot, value) scorer: the entity schema, if structure mode is more than five percentage points of micro-F1 below it; the task is then named "slot filling to JSON". fr-FR reuses the chosen representation unchanged.
8. **LoRA targets** - the Optuna layer-group search space always includes the needed task head (the package default leaves the extraction head frozen). Search space: `["encoder", "all_task_heads"]` (131 linear layers, asserted at runtime), `["all_task_heads"]`, `["encoder", <this task's head>]`. The winner is frozen per task. With LoRA, only `task_lr` is used.
9. **Training augmentation** - package defaults add synthetic label names, drop 20% of relation instances, drop classification labels and JSON fields. The Optuna search (design section 12) decides it: one on/off switch for augmentation, next to the LoRA layer-group choice (kept from section 12). The winner is frozen per task and recorded in every run log.
10. **Checkpoint** - `metric_for_best` = our dev micro-F1 via `compute_metrics`, `greater_is_better=True`. After training, reload `best` (the trainer keeps the last weights in memory).
11. **Vendor-inspired trial** - Fastino's recommended LoRA recipe (r and alpha by data size, `task_lr` 5e-4, augmentation on) is enqueued as trial 0 of every Optuna search, within the 20 trials; its dev score is reported. It is called "vendor-inspired" because our targets and step budget differ from the tutorial.
12. **CrossRE decoding** - scored as (head start, head end, tail start, tail end, relation type): direction kept, several relation types per pair kept, entity types not counted. Predictions use the package decoder as is (it expands contained mentions and merges repeated surface forms) with offsets from `include_spans`. Training labels are surface strings, and the package marks every occurrence. O2 audits the share of gold relation arguments whose surface form repeats in the sentence; if above 2%, results are also reported without those sentences (descriptive).

## 4. Package layout

```
src/active_gliner/
  cli.py            active-gliner <command>
  config.py         run config (pydantic), loaded from configs/*.yaml
  data/             one loader per dataset -> common records; split freezing; checks
  tasks/            ner.py, relations.py, classification.py, slots.py
                    each: schema, to_training_example, predict, sentence_confidence,
                    score (metrics), teacher prompt + validator
  model.py          load pinned student, fresh per run, flat decoder, word splitter
  candidates.py     below-threshold slot scores: same schema, threshold 0.0, overlap_policy allow
  selection.py      min, random, diversity (+ thesis scores), seeded tie-breaks
  teachers/         client.py, cache.py, stats.py
  train.py          ExtractorTrainer wrapper: LoRA, dev F1 hook, best checkpoint
  evaluate/         metrics.py, reports.py, calibration.py, errors.py
  observe/          logs.py, resources.py, plots.py, mlflow.py (optional)
  tune.py           Optuna search on dev (design section 12), trial histories saved
  report.py         run report card (markdown + PNG)
  analysis/         aggregate.py (reads run folders), stats.py (bootstrap, Holm, ASO),
                    figures.py (hero, Pareto, quadrant charts)
configs/            one YAML per run type in the matrix
tests/              pytest, Claude writes them
```

Each task plug-in is one file with the same six functions. A junior engineer reads one file to understand one task.

## 5. One run on disk

```
runs/<task>/<dataset>/<locale>/<arm>/<selector>-N<n>-seed<s>/
  config.yaml          the resolved config
  pins.json            model sha, package versions, dataset revision, git commit
  selected_ids.json    the ids picked, with their confidence
  train_log.jsonl      one line per logging step (loss, lr, throughput, GPU, CPU)
  eval_log.jsonl       one line per dev evaluation (dev F1, dev loss)
  metrics.json         final dev and test scores, wall time, GPU time
  per_type.csv         per label: P, R, F1, TP, FP, FN, support, mean confidence
  calibration.csv      4 bins: count, mean confidence, correctness
  errors.jsonl         every FP and FN with text, span, label, confidence, error kind
  predictions/         full dev and test predictions with confidence (for bootstrap and calibration)
  pool_scores.jsonl    confidence of every pool sentence at selection time
  hashes.json          split ids, schema, prompt, config hashes
  plots/training_curves.png, plots/calibration.png, plots/confusion.png
  report.md            one-page summary with the numbers and plots
  adapter/best/        PEFT adapter
```

Aggregate scripts read only these files. Paper numbers come from them by script.

Reproducibility details:

+ Seeds - one run seed gives three separate random streams (selection tie-breaks, data order, LoRA initialisation), derived with fixed offsets and written to `config.yaml`.
+ `pins.json` also holds teacher model revision, decoding settings and a label-cache fingerprint.
+ `metrics.json` holds the best step, its dev score, and the stop reason.
+ Tuning writes every trial (params, dev score per eval, state) under `runs/tuning/<task>/`.

Live logging bridge: returned histories arrive only at the end. We subclass `ExtractorTrainer` and override `_log_metrics` to append each training log line to `train_log.jsonl` as it happens; the same override writes the `prefix="eval"` branch (dev loss from the trainer plus our dev F1 from `compute_metrics`) to `eval_log.jsonl`, so each dev record is complete. `_log_metrics` is private, so `gliner2` stays pinned at 2.0.0 and a test checks the bridge.

## 6. How you follow a run

```
active-gliner run configs/ner_cleanconll.yaml --seed 1
   │
   ├── console + logs/run.log      live loss and dev F1 every eval step
   ├── train_log / eval_log.jsonl  open in the notebook, or `active-gliner watch <run dir>`
   ├── plots/*.png                 written at the end (and at each eval if --live-plots)
   └── report.md                   final one-page card, links to errors.jsonl
```

+ `active-gliner watch` prints a live table from the JSONL logs.
+ `active-gliner errors <run dir>` prints the worst errors, grouped by kind and by confidence bin.
+ The notebook `notebooks/quickstart.ipynb` is rebuilt on the new package: load, predict, one small LoRA run, curves, errors.
